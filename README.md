# VIPS Library RFID — Production Application

A separate, production-oriented RFID library entry/exit system built with Next.js 16, React 19, MongoDB Atlas and Mongoose.

## What is included

- Authenticated admin dashboard
- Live occupancy and hourly footfall
- Student ↔ RFID directory
- Manual student CRUD and CSV bulk import
- Complete visit history and CSV export
- Reader fleet health (heartbeat, RSSI, clock state, offline queue)
- Raw immutable-ish scan-event audit log
- ESP32 device enrollment with per-device secret
- Device heartbeat and time endpoints
- Idempotent RFID scan endpoint
- Cross-reader duplicate suppression
- Transactional visit projection
- Correct handling of delayed/offline scan timestamps
- 6:00 PM IST automatic close with `AUTO_6PM` audit method
- Admin login rate limiting
- Secure HttpOnly browser session cookie
- Vercel cron configuration
- Health endpoint
- ESP32 firmware copy under `firmware/`

## Stack

- Next.js 16 App Router / React 19
- TypeScript
- MongoDB Atlas
- Mongoose
- Zod validation
- JOSE signed admin-session JWTs
- Node `scrypt` password hashing
- Vanilla production CSS (no UI framework required)

## 1. MongoDB Atlas

Use a MongoDB Atlas cluster because scan processing uses multi-document transactions. Create a project/cluster and database user, then obtain the Drivers connection string.

Create `.env.local` from `.env.example`:

```bash
cp .env.example .env.local
```

Set:

```env
MONGODB_URI=mongodb+srv://...
MONGODB_DB=vips_library
SESSION_SECRET=<at least 32 random characters>
DEVICE_ENROLLMENT_KEY=<long random provisioning key>
CRON_SECRET=<long random cron secret>
ADMIN_EMAIL=library.admin@vipstc.edu.in
ADMIN_PASSWORD=<strong initial admin password>
NEXT_PUBLIC_INSTITUTION_NAME=VIPS Library
NEXT_PUBLIC_LIBRARY_CAPACITY=100
```

Never commit `.env.local`.

## 2. Install and initialize

Node.js 20.9+ is required by current Next.js 16.

```bash
npm install
npm run db:indexes
npm run seed:admin
npm run dev
```

Open `http://localhost:3000` and sign in with `ADMIN_EMAIL` / `ADMIN_PASSWORD`.

`npm run db:indexes` is important in production. It explicitly creates/synchronizes the unique and partial indexes that enforce RFID uniqueness, event idempotency and one open visit per student.

## 3. Import students

Dashboard → **Students** → **Import CSV**.

Required headers:

```text
enrollmentNumber,name,rfidUid
```

Optional:

```text
course,batch,section
```

A sample is included at `sample-data/students.csv`.

The RFID UID must be the decimal UID generated by the ESP firmware, not the raw 12-character EM-18 frame.

## 4. ESP32 firmware

The matching firmware is included at:

```text
firmware/VIPS_Library_RFID_Gate.ino
```

Before flashing, edit:

```cpp
#define BACKEND_URL "https://YOUR-PRODUCTION-DOMAIN"
#define ENROLLMENT_KEY "SAME_VALUE_AS_DEVICE_ENROLLMENT_KEY"
```

Provisioning flow:

1. Flash ESP32.
2. Configure its 2.4 GHz Wi-Fi from the local setup portal.
3. On first successful internet connection it calls `POST /api/device/register`.
4. The server returns a unique per-reader secret.
5. The ESP stores that secret locally and uses it for heartbeat and scan requests.

After all production readers are enrolled, treat `DEVICE_ENROLLMENT_KEY` like a master provisioning credential. Rotate it if it is exposed.

## 5. Device API contract

### POST `/api/device/register`

Header:

```text
x-enrollment-key: <DEVICE_ENROLLMENT_KEY>
```

Body:

```json
{
  "macAddress": "AA:BB:CC:DD:EE:FF",
  "name": "VIPS Library Gate",
  "firmwareVersion": "1.0.0",
  "deviceType": "LIBRARY_GATE"
}
```

### GET `/api/device/time`

Returns Unix seconds for ESP fallback clock synchronization.

### POST `/api/device/heartbeat`

Headers:

```text
x-device-mac
x-device-secret
```

Tracks last seen, RSSI, offline queue depth, firmware version and clock status.

### POST `/api/library/scan`

Body:

```json
{
  "eventId": "unique-reader-event-id",
  "rfidUid": "2053291",
  "scannedAt": "2026-07-30T10:31:14+05:30",
  "firmwareVersion": "1.0.0"
}
```

The ESP does **not** decide IN or OUT. The backend projects accepted events chronologically and returns the authoritative direction.

## 6. Why delayed/offline scans are safe

The backend stores the physical scan timestamp (`scannedAt`) separately from network receipt time (`receivedAt`). For a valid student/day it reconstructs that student's visit sequence using ordered event timestamps.

This means an event scanned at 10:31 and uploaded at 10:38 is still placed at 10:31. It also means queued scans arriving after later scans can be reconciled into their correct chronological position.

Each `eventId` is unique, so an ESP retry after a lost HTTP response cannot accidentally turn an IN into an OUT.

## 7. 6 PM closure

`vercel.json` configures:

```text
30 12 * * *
```

Vercel cron expressions are UTC, and 12:30 UTC is 18:00 IST.

The endpoint is `/api/cron/auto-close` and verifies:

```text
Authorization: Bearer <CRON_SECRET>
```

Open visits are closed with their **stored OUT timestamp set to exactly 18:00 IST**, and `outMethod = AUTO_6PM`.

The dashboard also performs an idempotent due-close check before live reads, so if a scheduled invocation is delayed, the data self-corrects on the next dashboard access. This is useful on hosting tiers whose cron execution can be delayed.

## 8. Deploy to Vercel

Push this folder to its own GitHub repository, import it into Vercel, and add all environment variables from `.env.example` in Project Settings → Environment Variables.

After deployment:

1. Run `npm run db:indexes` once against the production Atlas database from a trusted machine with the production env vars.
2. Run `npm run seed:admin` once.
3. Confirm `/api/health` returns `status: ok`.
4. Confirm the Vercel Cron Job appears for `/api/cron/auto-close`.
5. Update `BACKEND_URL` in the ESP firmware to the production HTTPS domain.
6. Flash and enroll one physical reader before rolling out the rest.

## 9. Security notes

- Browser sessions are signed, HttpOnly, SameSite=Strict cookies.
- Admin passwords are never stored in plaintext.
- ESP per-device secrets are returned once and stored server-side only as SHA-256 hashes.
- Device writes require both MAC and secret.
- Admin mutation APIs enforce same-origin requests in addition to authenticated sessions.
- Login failures are throttled in MongoDB.
- The database connection string stays server-side; ESP32 devices never receive MongoDB credentials.
- The firmware currently uses `WiFiClientSecure.setInsecure()` for TLS transport compatibility. Before a high-assurance production rollout, pin/validate the server CA certificate in firmware.

## 10. Production verification checklist

Before deploying all readers:

- `npm run lint`
- `npm run build`
- `npm run db:indexes`
- Test one student IN → OUT
- Test duplicate scans within 5 seconds across two readers
- Disconnect Wi-Fi, scan, reconnect, verify original `scannedAt`
- Retry the exact same event ID and verify state does not toggle
- Test unknown RFID
- Test scan before 09:00 and after 18:00
- Test open visit auto-closes to exactly 18:00 with `AUTO_6PM`
- Disable a reader from dashboard and verify its device API auth fails
- Export visit CSV and compare against dashboard history


## CDC placement attendance portal

The same application now contains a separate Career Development Centre attendance area under `/cdc`.

Current CDC scope:

- Separate CDC student, placement-session and attendance collections
- Completely separate CDC authentication from the Library portal
- Dedicated CDC administrator collection, login and session cookie
- CSV roster import with enrollment-number decoding and programme-code validation
- Card ID or enrollment-number attendance capture
- Session-level programme eligibility
- Database-level duplicate attendance prevention
- Open / close attendance registers
- Session attendance CSV export
- No CDC attendance data is written to the library visit collections

Approved B.Tech programme codes are:

```text
027 CSE
116 AIML
117 IIOT
119 AIDS
135 Computer Science - Cyber Security
160 VLSI
495 CSAM
```

The first roster prepared for import contains the 481 confirmed 2023 B.Tech students from codes 027, 116, 117, 119 and 160. Codes 072, 084 and 085 are intentionally excluded until they are verified.

CDC roster CSV requires:

```text
enrollmentNumber,name,cardId
```

Optional columns include `program` and `department`. Enrollment metadata is decoded server-side, so shortened enrollment numbers are left-padded to 11 digits before validation.

Configure separate CDC credentials in the deployment environment:

```env
CDC_ADMIN_EMAIL=cdc@vipstc.edu.in
CDC_ADMIN_PASSWORD=<deployment secret>
CDC_ADMIN_NAME=CDC
```

Then provision the CDC account and indexes:

```bash
npm run seed:cdc-admin
npm run db:indexes
```

CDC staff sign in only at `/cdc/login`. Library sessions do not grant CDC access, and CDC sessions do not grant Library access.

Run the index command before importing the roster so the unique CDC enrollment, Card ID and per-session attendance indexes are enforced in production.
